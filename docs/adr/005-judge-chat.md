# ADR-005: Обсуждение вердикта с судьёй — синхронный POST, переписка в БД, вердикт неизменен

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

Пользователь хочет после вердикта обсудить результаты с судьёй: переспросить, оспорить
вывод, принести довод, которого не было в материале. Вердикт — главный результат, его
читают вместо транскрипта; чат — продолжение того же разбора, а не новый.

## Decision

1. **`POST /api/analyses/{id}/chat` синхронный**: запрос ждёт ответ судьи и возвращает
   обе реплики. Ответ — одна реплика той же длины и effort, что у аналитика (на Opus
   5.5 — 18–30 с по замеру, README «Measurements»); индикатора «судья думает…» достаточно. SSE и фоновая задача не нужны: событие одно, подписчик один.
2. **Контекст — каждый раз целиком** в одном `user`-сообщении: материал, транскрипт,
   вердикт JSON, предыдущая переписка, новое сообщение. Порт `ChatProvider` не меняется
   (single-turn `system + user`), как уже сделано с транскриптом аналитиков.
3. **Переписка — отдельная таблица `judge_messages`**, `create_all` создаёт её и на
   существующей БД без миграции. Обе реплики пишутся только после успешного ответа:
   падение модели не оставляет вопросов без ответа.
4. **Вердикт неизменен.** Судья может пересмотреть оценку в чате и обязан сказать это
   явно, но сохранённый `Verdict` не переписывается: вердикт — результат протокола
   (слепой раунд, перекрёстная проверка), а чат — разговор одного судьи с одним человеком.
5. **Против угодливости** — правило промпта: оценка меняется только под весом доводов или
   новых фактов; нажим и несогласие без аргументов — не довод. Новые факты пользователя
   несут бремя доказывания.
6. **Анонимизация** сохраняется: клиент присылает `legend` (метка → имя) вместе с
   сообщением, сервер заменяет упоминания по правилам §4.0b и не сохраняет легенду.
7. Только веб. Бот и CLI — без чата (README «Cut scope»).

## Alternatives considered

1. **Ответ через SSE / потоковые токены.** Живее; rejected: потоковые токены уже вне scope
   (SPEC §1), а событие ровно одно — SSE ради него лишний механизм.
2. **Multi-turn `messages` в порту.** Ближе к нативному чату; rejected: меняет порт и оба
   провайдера ради того, что одна длинная `user`-реплика делает так же; вернуться, если
   понадобится prompt caching по префиксу.
3. **Пересчитывать вердикт по итогам чата.** rejected: смешивает протокол команды с
   разговором одного человека; вердикт стал бы зависеть от настойчивости пользователя.
4. **Чат с аналитиками.** rejected: просили судью; три голоса в ответ на вопрос — снова
   дискуссия, а не ответ.

## Consequences

- Каждое сообщение — полный контекст разбора в модель (~20–30k входных токенов на Opus
  5.5); число сообщений ограничено JUDGE_CHAT_MAX_MESSAGES (SPEC §7).
- Блокировка «один ответ за раз на разбор» живёт в памяти процесса — как и реестр
  разборов (ADR-003).
- Соединение висит до ответа судьи: прокси с таймаутом < 60 с его оборвут (Cloud Run по
  умолчанию — 300 с).

## Revisit when

- Ответ судьи в чате регулярно > 60 с или прокси обрывают запрос — перейти на фоновую
  задачу + SSE.
- Переписки длиннее 10 сообщений обычны — добавить prompt caching по неизменному префиксу.
