# ADR-005: Деплой веба на Google Cloud Run: один инстанс, SQLite с репликацией Litestream в GCS, доступ через IAP

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

Нужен постоянный адрес в интернете для веб-интерфейса без своего сервера. Выбран личный
GCP-проект `ivan-pets`, Cloud Run, регион `europe-west1`, бюджет $5/мес. Из ADR-003 вытекают
три ограничения:

- события разбора живут в памяти процесса, а сам разбор — фоновая `asyncio`-задача, которая
  длится минуты (замер: 216 с на 3 раунда);
- файловая система Cloud Run эфемерна: SQLite пропадает при каждом скейле в ноль;
- приложение без авторизации (SPEC, «Cut scope»), а за каждым разбором стоят деньги на
  ключе Anthropic.

## Decision

1. **Один инстанс, CPU всегда выделен:** `--max-instances 1 --min-instances 0
   --no-cpu-throttling`. Один инстанс гарантирует, что POST и SSE попадут в один процесс с
   реестром событий. Постоянный CPU нужен, чтобы фоновый разбор не замирал, когда вкладку
   закрыли. Таймаут запроса 3600 с — под SSE-поток.
2. **SQLite + Litestream → GCS.** `deploy/entrypoint.sh` при заданном
   `LITESTREAM_REPLICA_URL` восстанавливает базу из бакета `gs://ivan-pets-litestream`
   (если реплика есть), выставляет `DATABASE_URL` на этот файл и запускает приложение под
   `litestream replicate -exec`. Каждая запись уходит в бакет примерно за секунду. Без
   переменной entrypoint ничего не делает — локальный запуск и `docker compose` не меняются.
3. **Litestream 0.3.13, а не 0.5.x.** На 0.5.17 GCS-реплика молча не пишет ни одного
   объекта (воспроизведено локально; benbjohnson/litestream#1512, плюс открытые #1537 и
   #1164 про компакцию и восстановление на GCS). 0.3.13 проверена end-to-end: разбор
   пережил уничтожение контейнера и восстановился в новом. Схема URL — `gcs://`.
4. **Доступ — Identity-Aware Proxy на самом сервисе** (`--no-allow-unauthenticated --iap`):
   Google-логин, пускает только явно добавленные аккаунты (`roles/iap.httpsResourceAccessor`).
   Код и SPEC не меняются, авторизация остаётся вне приложения.
5. **Ключ Anthropic — Secret Manager** (`anthropic-api-key`), в сервис попадает через
   `--update-secrets`.
6. **Только веб.** Telegram-бот работает long polling без входящих запросов и в модель
   Cloud Run не ложится; он остаётся на `docker compose`.

## Alternatives considered

1. **Neon / Supabase Postgres** (бесплатный внешний Postgres). Код уже умеет Postgres;
   rejected пользователем: всё должно жить в Google Cloud.
2. **Cloud SQL Postgres.** Управляемый, без правок; rejected: от ~$10/мес, вдвое выше
   бюджета личного проекта.
3. **GCS-бакет, смонтированный как том под SQLite.** rejected: gcsfuse не даёт блокировок
   и переписывает объект целиком — база побьётся.
4. **Firestore.** Бесплатный тариф; rejected: переписывание слоя репозитория ради деплоя.
5. **Публичный URL без авторизации.** rejected: любой нашедший адрес тратит ключ.
6. **Авторизация в приложении.** rejected: вне SPEC (Cut scope); IAP решает задачу снаружи.

## Consequences

- При выкатке новой ревизии Cloud Run несколько секунд держит старый и новый инстанс; если
  в этот момент идёт разбор, его записи могут не попасть в новую реплику. Для личного
  инструмента приемлемо; выкатывать лучше, когда разборов нет.
- На SIGTERM у инстанса 10 с: Litestream передаёт сигнал приложению и делает финальную
  синхронизацию. Окно потери — последние ~1 с записей при жёстком убийстве.
- Инстанс живёт до ~15 мин после последнего запроса, и при `--no-cpu-throttling` всё это
  время оплачивается. При личном использовании это внутри бесплатной квоты Cloud Run.
- Горизонтального масштабирования нет — как и в ADR-003.

## Revisit when

- Нужен второй инстанс или второй пользователь с параллельными разборами — тогда шина
  событий (ADR-003) и Postgres.
- Litestream 0.5.x закроет GCS-баги — можно обновиться, формат реплики при этом сменится
  (потребуется новая реплика).
