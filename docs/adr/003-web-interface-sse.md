# ADR-003: FastAPI + одностраничный фронтенд без сборки; живой ход разбора через SSE; события в памяти, факты в БД

- **Status:** Accepted
- **Date:** 2026-10-11

## Context

Нужен «простой симпатичный UI», где видно ход и результат дискуссии. Разбор длится
минуты, реплики появляются по одной. Проект личный, деплой — один процесс (Docker),
без CDN и фронтенд-сборки.

## Decision

1. **FastAPI** (`interface/api`) с JSON-эндпоинтами из SPEC §3; фронтенд — статические
   `index.html + app.js + styles.css` (vanilla JS, CSS-переменные, тёмная/светлая тема),
   раздаются тем же приложением. Никакого bundler/npm.
2. **SSE** (`GET /api/analyses/{id}/events`) через `StreamingResponse`: replay сохранённых
   событий + live, heartbeat 15 с. Не WebSocket: поток односторонний, SSE переживает
   прокси и переподключается браузером сам.
3. `application/service.py` держит in-memory реестр активных разборов: список событий и
   `asyncio.Condition` для подписчиков. Реплики и вердикт пишутся в БД сразу, чтобы после
   рестарта история была полной; события для завершённых разборов восстанавливаются из БД.
4. Запуск разбора — `asyncio.create_task` внутри процесса (как в первой версии для бота);
   отдельной очереди задач нет.

## Alternatives considered

1. **React/Vite.** Удобнее для сложного UI; rejected: один экран, тянуть node-сборку в
   Python-проект ради него неоправданно.
2. **WebSocket.** rejected: двусторонность не нужна; SSE проще и совместимее.
3. **Polling `GET /analyses/{id}` раз в 2 с.** Проще всего; rejected: при 7 вызовах по
   20–40 с — десятки пустых запросов, а задержка появления реплики заметна.
4. **Очередь задач (arq/celery).** rejected: один процесс, личное использование; при
   рестарте незавершённые разборы честно помечаются `failed/interrupted` (SPEC §6 №5).

## Consequences

- Горизонтальное масштабирование невозможно без выноса шины событий (Redis) —
  сознательно.
- Фронтенд рендерит реплики как текст с минимальной разметкой (абзацы, жирные маркеры
  «Принимаю/Оспариваю/Уточняю»); полный markdown не в scope.

## Revisit when

- Нужен второй процесс/воркер или > 1 одновременного пользователя с ожиданием > 5 разборов.
