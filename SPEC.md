# SPEC — Rational Check (Проверка здравого смысла)

> Behavior specification, written before implementation. If observed behavior deviates
> from this spec, either the code or this document has a bug. There is no hidden
> hardcoded behavior.

## 1. Purpose and scope

Главная цель приложения — **найти истину**, а не победителя. Пользователь присылает
текст (пост, статью, аргумент, тезис) **или диалог** нескольких собеседников. Три
**рациональных аналитика** — LLM-агенты без философских школ, апологеты рационального
мышления по Манифесту здравого смысла — это **одна команда**: они независимо разбирают
материал, затем перекрёстно проверяют друг друга, критикуя слабые места и **явно принимая**
рациональные доводы коллег, чтобы вместе приблизиться к наиболее вероятной картине.
**Судья не выбирает победителя**: он формулирует то, что ближе всего к истине, разделяет
доказанное / вероятное / непроверяемое, называет уловки, критерий опровержения и
практическое следствие. Для диалога судья дополнительно оценивает **близость каждого
собеседника к истине** и называет, чья позиция ближе всего, с объяснением, что верно у
каждого. Аналитики не оцениваются и не ранжируются.

In scope:
- Два режима входа: **текст** (один автор) и **диалог** (≥ 2 собеседника, реплики
  вида «Имя: текст»); режим `auto` распознаёт диалог сам (§4.0).
- Web UI (одна страница): ввод текста, живой ход разбора, карточка вердикта, история.
- HTTP API + SSE для того же.
- Провайдеры LLM: Anthropic (по умолчанию) и DeepSeek; mock-режим без ключей.
- Telegram-бот как второй тонкий интерфейс (`/check <текст>`).
- **Обсуждение вердикта с судьёй** (§4.6): после вердикта пользователь задаёт судье
  вопросы и спорит с выводами в чате под карточкой вердикта; судья отвечает по Манифесту.
- **Публикация разбора** (§4.7): завершённый разбор публикуется статической страницей по
  неугадываемой ссылке, которая открывается у кого угодно без доступа к приложению.

Out of scope (cut consciously):
- Аутентификация, мультипользовательность, квоты. Инструмент личный / для одного чата.
- Потоковая выдача токенов внутри реплики (SSE отдаёт реплики целиком).
- Веб-поиск и проверка фактов по внешним источникам: аналитики работают только с текстом
  и своими знаниями, и обязаны это явно помечать.
- Редактирование аналитиков через UI/БД: аналитики описаны в коде (ADR-002).
- Лидерборд персон из первой версии — удалён вместе с персонами-философами.
- Любые баллы аналитикам, «самый рациональный аналитик», коронки — удалены сознательно:
  аналитики ищут истину сообща, а не соревнуются.

## 2. Data

- `Analysis` — один разбор: `id`, `source_text`, `question` (что именно проверить,
  опционально), `mode` (`text|dialogue`), `participants` (имена собеседников, JSON; пусто
  для текста), `rounds`, `model_analyst`, `model_judge`, `status`
  (`running|finished|failed`), `error`, `created_at`, `finished_at`, `duration_ms`,
  `title` (первые 80 символов текста без переносов).
- `Turn` — реплика аналитика: `analysis_id`, `round_no`, `analyst`, `emoji`, `text`,
  `created_at`.
- `VerdictRecord` — вердикт судьи: `analysis_id`, `payload` (JSON ровно по Pydantic-схеме
  `Verdict`, §3.3), `created_at`.
- `JudgeMessage` — реплика обсуждения вердикта (§4.6): `analysis_id`, `role`
  (`user|judge`), `text`, `created_at`. Удаляется вместе с разбором.
- `Share` — публикация разбора (§4.7): `analysis_id` (уникален), `key` (случайный токен),
  `url`, `created_at`. Удаляется вместе с разбором.
- Аналитики (`AnalystSpec`) — в коде, `domain/analysts.py`.

## 3. API contract

Pydantic-схемы в `debate_arena/interface/api/schemas.py` (DTO) и
`debate_arena/domain/schemas.py` (`Verdict`, `AnalystSpec`) — единственный источник
контракта. Префикс `/api`.

### 3.1 `POST /api/analyses` → 202

Запрос `AnalysisRequest`: `text` (1..MAX_TEXT_CHARS символов после strip), `question`
(опционально, ≤ 500), `rounds` (1..MAX_ROUNDS, по умолчанию DEFAULT_ROUNDS), `model`
(опционально, один из `GET /api/config.models`), `mode` (`auto|text|dialogue`, по
умолчанию `auto`). Ответ `{"id": int, "legend": {метка: имя}}` (`legend` пуст для текста и
при выключенной анонимизации). Ошибки: 422 — валидация, в том числе
`mode=dialogue` при < 2 распознанных собеседниках; 503 — LLM-провайдер не
сконфигурирован (не бывает в mock-режиме).

### 3.2 `GET /api/analyses/{id}` → 200 `AnalysisDetail`

`id, title, source_text, question, mode, participants[], rounds, status, error,
created_at, finished_at, duration_ms, analysts[], turns[], verdict|null, chat[],
share|null`. 404 если нет. `chat` — реплики обсуждения с судьёй `{role, text, created_at}`
в порядке появления. `share` — `{url, created_at}`, если разбор опубликован (§3.6a).

### 3.3 `Verdict` (структурированный вывод судьи)

| Поле | Тип | Смысл |
|---|---|---|
| `core_question` | str | де-фрейминг: нейтральная формулировка предмета |
| `conclusion` | str | **то, что ближе всего к истине** — сам ответ, 2–4 предложения |
| `narrative` | str | **развёрнутое обоснование**, JUDGE_NARRATIVE_WORDS слов в 4–7 абзацах: предмет и де-фрейминг, что установлено и почему, граница доказанного и интерпретаций, решающие и отпавшие доводы аналитиков, неопределённость, почему именно это ближе к истине (в диалоге — по каждому собеседнику). Главный текст приложения |
| `rationality_score` | int 0..100 | насколько рационален исходный материал (текст или диалог в целом) |
| `confidence` | int 0..100 | уверенность судьи в заключении |
| `established` | list[str] | что доказано строго |
| `probable` | list[str] | рациональная рабочая гипотеза (Оккам) |
| `uncertain` | list[str] | честные белые пятна |
| `claims` | list[ClaimAssessment] | ключевые утверждения и их статус; `by` — кто утверждал (диалог) |
| `fallacies` | list[Fallacy] | найденные уловки (имя, цитата, объяснение, `by`) |
| `steelman` | str | сильнейшая версия позиции автора (текст) или спорного тезиса (диалог) |
| `falsification` | str | что должно появиться, чтобы вердикт изменился |
| `so_what` | str | практическое следствие |
| `consensus` | list[str] | на чём аналитики сошлись после перекрёстной проверки |
| `open_questions` | list[str] | где аналитики не сошлись или что осталось открытым |
| `participants` | list[ParticipantAssessment] | диалог: по одному на собеседника; текст: пусто |
| `closest_to_truth` | str \| null | диалог: имя собеседника, чья позиция ближе всего к истине; текст: null |

`ParticipantAssessment`: `name`, `truth_proximity` 0..100 (близость позиции к истине),
`position` (позиция своими словами), `right_about` (что у него верно), `wrong_about`
(главная ошибка или пусто), `note`.
`ClaimAssessment.status ∈ {supported, plausible, unsupported, unfalsifiable, false}`.

Вердикт — главный результат: пользователь читает его вместо транскрипта, поэтому судья
пишет **полно**: списки по 3–8 пунктов с обоснованием в одно-два предложения (не ярлыки),
`claims` — все ключевые утверждения, `participants.*` — развёрнуто. Полнота — охват, не вода.
Старые вердикты без `narrative` остаются валидными (поле по умолчанию пустое).

**Invariants:** в режиме диалога `participants` содержит ровно по одной записи на каждого
распознанного собеседника и `closest_to_truth` ∈ их имена; в режиме текста
`participants = []` и `closest_to_truth = null`; все числа в диапазонах; `conclusion`
непуст. Аналитики в вердикте не оцениваются. Невалидный вердикт от модели → одна
повторная попытка, затем `status=failed`.

### 3.4 `GET /api/analyses/{id}/events` → `text/event-stream`

Сначала replay всех уже случившихся событий, затем live. События (поле `event`, данные —
JSON): `started {analysts, rounds}`, `round {round_no, kind}`, `typing {analyst}`,
`turn {round_no, analyst, emoji, text}`, `verdict {…Verdict}`, `error {message}`,
`done {status}`. После `done` соединение закрывается. Heartbeat-комментарий каждые
SSE_HEARTBEAT_S секунд. Для завершённого разбора (после рестарта сервера) события
восстанавливаются из БД: `started`, `turn`×N, `verdict`, `done`.

### 3.5 `POST /api/analyses/{id}/chat` → 200 — вопрос судье

Запрос `ChatRequestIn`: `text` (1..JUDGE_CHAT_MAX_CHARS после strip), `legend`
(опционально, `{метка: имя}` из ответа 202 — только для анонимизации сообщения, на сервере
не сохраняется). Ответ `ChatExchange {question, reply}` — обе реплики `{role, text,
created_at}` в том виде, в каком они сохранены (с метками вместо имён). Ответ синхронный:
запрос ждёт судью. Ошибки: 404 — нет разбора; 409 — у разбора нет вердикта (идёт или
упал), судья ещё отвечает на предыдущее сообщение этого разбора, или исчерпан лимит
JUDGE_CHAT_MAX_MESSAGES; 422 — валидация; 502 — модель отказалась или провайдер упал
(ничего не сохраняется, можно повторить); 503 — провайдер судьи этого разбора не
сконфигурирован.

### 3.6a Публикация — `POST` / `DELETE /api/analyses/{id}/share`

`POST` → 200 `ShareOut {url, created_at}`: публикует снимок (§4.7). Повторный `POST`
возвращает ту же ссылку и ничего не перезаливает. Ошибки: 404 — нет разбора; 409 — у
разбора нет вердикта (идёт или упал); 502 — хранилище снимков недоступно (ничего не
сохраняется, можно повторить). Текст 502 фиксированный, «snapshot storage is
unavailable»: подробности (бакет, пути, ответ хранилища) остаются в логе сервера.

`DELETE` → 204: снимает с публикации (объект удаляется из хранилища, запись из БД).
Ошибки: 404 — нет разбора или он не опубликован; 502 — хранилище недоступно (запись
остаётся, можно повторить).

### 3.6 Прочее

- `GET /api/analyses?limit=N` → `AnalysisSummary[]` (новые первыми, `limit` ≤ HISTORY_LIMIT).
- `DELETE /api/analyses/{id}` → 204 (запущенный удалить нельзя → 409; пока судья отвечает
  в чате — тоже 409). Опубликованный разбор сначала снимается с публикации; если хранилище
  снимков недоступно — 502, и разбор не удаляется.
- `GET /api/config` → `{models: [{id, label, provider}], default_model, default_rounds,
  max_rounds, max_text_chars, mock: bool, analysts: [{name, emoji, focus}],
  chat_max_chars, chat_max_messages, share_backend}`. `share_backend` ∈ `gcs|local`
  (§4.7): куда уходят снимки.
- `GET /health` → `{status, version, mock}`.
- `GET /` → `index.html` фронтенда.

## 4. Pipeline (normative behavior)

0. **Режим.** `mode=text|dialogue` берётся как есть; `auto` → диалог, если парсер (§4.0a)
   нашёл ≥ 2 собеседников и либо реплики с автором составляют ≥ DIALOGUE_LINE_SHARE
   строк текста, либо реплик ≥ DIALOGUE_MIN_MESSAGES (длинные многострочные сообщения),
   иначе текст. Парсер (`domain/dialogue.py`): строка вида `Имя: текст`, `Имя — текст`,
   `[Имя] текст`, `**Имя:** текст`, а также `Имя:` на отдельной строке с телом ниже
   (экспорт из мессенджеров); допускаются маркеры цитаты `>` и буллеты в начале строки и
   необязательная метка времени; имя ≤ DIALOGUE_NAME_CHARS символов, ≤ 4 слов; строки без
   автора приписываются предыдущему, маркеры цитаты с них снимаются. В диалоге аналитики и судья получают список собеседников.
0b. **Анонимизация** (`ANONYMIZE_PARTICIPANTS`, по умолчанию включена). В режиме диалога
   реальные имена собеседников не попадают ни в модель, ни в БД: каждая реплика
   переписывается как `Собеседник А: текст` (метки А, Б, В… по порядку первого
   появления; для нерусского `LANGUAGE` — `Participant A`), а упоминания имён внутри
   реплик заменяются на метку. Замена упоминаний: точное имя без учёта регистра, плюс
   основа имени (имя без последней гласной, если основа ≥ 3 символов) с 1–3 буквами
   окончания — так ловятся падежи (Ивана, Иваном, Марии). Побочный эффект принят
   сознательно: похожие имена (Марина при собеседнике Мария) тоже заменяются — ложная
   замена безопаснее утечки. Для латинских имён дополнительно заменяется их кириллическая
   транслитерация (Vanya → Ваня, Friska → Фриска), потому что в русском чате собеседников
   зовут по-русски. Тем же правилам подчиняется `question`: «Кто прав, Иван или Мария?»
   сохраняется как «Кто прав, Собеседник А или Собеседник Б?». Аналитикам велено называть собеседников только так, как они подписаны. Соответствие «метка → имя» возвращается один раз в ответе
   `POST /api/analyses` (`legend`) и нигде на сервере не сохраняется; UI хранит его в
   браузере и может показывать настоящие имена только локально.
1. **Раунд 1 — Независимый разбор.** Каждый аналитик получает только текст (и
   `question`), без реплик коллег, чтобы исключить якорение. Все три вызова идут
   **параллельно**. Реплика структурирована по протоколу Манифеста: ядро тезиса → факты
   vs интерпретации → бремя доказывания / Оккам / уловки → сильнейшая версия → вывод.
2. **Раунды 2..N — Перекрёстная проверка.** Последовательно; каждый видит весь транскрипт.
   Обязательные блоки реплики: «Принимаю:» (рациональные доводы коллег, которые
   принимаются, с указанием чьи), «Оспариваю:» (ошибки коллег с объяснением),
   «Уточняю:» (собственная скорректированная позиция). Согласие под весом доводов —
   норма, не слабость; несогласие ради несогласия запрещено.
3. **Судья.** Получает материал, вопрос, список собеседников и весь транскрипт,
   возвращает `Verdict` строго по схеме (structured output у Anthropic; JSON-mode + схема в
   промпте у DeepSeek). Судья **не выбирает победителя** ни среди аналитиков, ни среди
   собеседников: `closest_to_truth` — это чья *картина* точнее, с обязательным
   `right_about` для каждого участника.
4. Каждая реплика и вердикт сохраняются в БД сразу, события публикуются подписчикам SSE.
5. Любая ошибка модели → `status=failed`, событие `error`, разбор остаётся в истории с
   сохранёнными репликами.
6. **Обсуждение вердикта** (ADR-005). Доступно только у разбора с вердиктом. Судья — та
   же модель, что выносила вердикт (`model_judge` разбора), effort JUDGE_CHAT_EFFORT.
   Один вызов `complete` на сообщение; судья получает материал, вопрос, собеседников,
   транскрипт аналитиков, свой вердикт (JSON) и всю предыдущую переписку, затем новое
   сообщение. Правила ответа (промпт):
   - по существу и по Манифесту; без выдуманных фактов, непроверяемое — «не могу
     проверить»;
   - **меняет оценку только под весом доводов или новых фактов** и говорит это явно
     («Пересматриваю: …, потому что …»); настойчивость, эмоции и апелляции к авторитету
     пользователя — не довод, позиция тогда сохраняется с объяснением;
   - новые факты пользователя — утверждения с бременем доказывания: судья может принять
     их условно («если это так, то …»), но не считает доказанными;
   - сохранённый вердикт не переписывается — пересмотр живёт только в переписке;
   - победителя по-прежнему нет; в диалоге собеседники называются метками;
   - объём — JUDGE_CHAT_WORDS слов, если пользователь не просит подробнее; абзацы без
     markdown-заголовков и таблиц.
   Анонимизация: если у разбора режим диалога и клиент прислал `legend`, упоминания имён
   в сообщении (по правилам §4.0b, включая падежи и транслитерацию) заменяются метками до
   модели и БД. Обе реплики сохраняются **только после** успешного ответа судьи, одной
   транзакцией. На один разбор одновременно отвечает не больше одного вызова судьи; вызов
   дольше JUDGE_CHAT_TIMEOUT_S прерывается (502), чтобы оборванный клиентом запрос не
   держал блокировку.

7. **Публикация** (ADR-006). Доступна только у разбора со статусом `finished` и вердиктом.
   Сервер собирает одну самодостаточную HTML-страницу: стили инлайн, без JS и внешних
   ресурсов, `noindex`. Состав: заголовок, дата, режим, вопрос, собеседники, вердикт
   целиком (все поля §3.3), исходный материал и реплики аналитиков по раундам. **Не
   входят:** обсуждение с судьёй и `legend`. В диалоге собеседники видны только метками,
   как в БД. Весь текст экранируется, разметку из реплик (`**жирный**`, блоки
   «Принимаю/Оспариваю/Уточняю») сервер переводит в HTML сам. Ключ —
   `secrets.token_urlsafe(SHARE_TOKEN_BYTES)`, объект `<key>.html` с `Cache-Control:
   public, max-age=SHARE_CACHE_MAX_AGE_S`. Хранилище: при заданном `SHARE_BUCKET` —
   бакет GCS со ссылкой `https://storage.googleapis.com/<bucket>/<key>.html`; иначе —
   каталог `SHARE_DIR`, который приложение раздаёт по `/shared/<key>.html` (ссылка
   абсолютная, если задан `PUBLIC_URL`, иначе от корня сайта). Запись `Share`
   сохраняется только после успешной загрузки. Если запись не сохранилась, загруженный
   объект удаляется. Публикация, снятие и удаление разбора идут под блокировкой на разбор
   (один процесс, §1). Поэтому одновременные `POST` дают одну ссылку и один объект, а
   удаление во время публикации не оставляет страницы. Строка «Имена собеседников заменены
   метками» есть в снимке, только если собеседники действительно названы метками (§4.0b).
   При `ANONYMIZE_PARTICIPANTS=false` в снимок идут настоящие имена, как и в БД.

Таблица отказов:

| Причина | Поведение |
|---|---|
| Провайдер вернул `stop_reason=refusal` | `error: "Модель отказалась разбирать этот текст"`, failed |
| Сетевая/5xx ошибка после ретраев SDK | `error` с классом ошибки, failed |
| Вердикт не прошёл схему дважды | `error: "Судья не дал валидный вердикт"`, failed |
| Ошибка/отказ модели в обсуждении вердикта | 502, переписка не меняется, разбор не трогается |
| Хранилище снимков недоступно при публикации / снятии / удалении разбора | 502, БД не меняется |
| Текст пуст / длиннее лимита | 422 до запуска |
| `mode=dialogue`, но собеседников < 2 | 422: «не удалось распознать собеседников; формат „Имя: реплика“» |

## 5. Constraints handling

- Язык реплик и вердикта — `LANGUAGE` (по умолчанию русский), подставляется в промпты.
- Аналитики не выдумывают источники: отсутствие данных формулируется как «не могу
  проверить», это требование Манифеста (п. 3 и 6).
- Один разбор = `3 × rounds + 1` вызовов LLM. Параллелизм ограничен семафором
  LLM_CONCURRENCY. Каждое сообщение судье — ещё один вызов с полным контекстом разбора
  (на Opus 5.5 ~20–30k входных токенов), поэтому число сообщений ограничено
  JUDGE_CHAT_MAX_MESSAGES. Вызов чата идёт мимо семафора LLM_CONCURRENCY сознательно: он
  один на разбор (блокировка §4.6), а ждать в очереди за раундом чужого разбора — минуты.

## 6. Edge cases (normative)

| # | Input | Required behavior |
|---|---|---|
| 1 | Пустой текст / только пробелы | 422 |
| 2 | Текст > MAX_TEXT_CHARS | 422 с сообщением о лимите |
| 3 | `rounds=1` | Только независимый разбор + судья, событие `round` одно |
| 4 | Подписка на SSE после завершения | Replay из памяти или БД, затем `done` |
| 5 | Рестарт сервера во время разбора | Разбор остаётся `running` в БД → при старте помечается `failed` с `error="interrupted"` |
| 6 | Неизвестный `model` в запросе (нет в `GET /api/config.models`) | 422 |
| 7 | Нет ключей и `MOCK_LLM` не задан | Приложение стартует в mock-режиме и явно пишет это в `/api/config.mock` и в UI |
| 8 | Текст без утверждений (вопрос, список покупок) | Судья обязан вернуть вердикт с `claims=[]` и объяснением в `conclusion` |
| 9 | `mode=auto`, текст с одной подписью «Автор: …» | Текст (один собеседник — не диалог) |
| 10 | Диалог, где оба собеседника частично правы | `closest_to_truth` — чья картина точнее; у обоих непустой `right_about`; `conclusion` объединяет верное |
| 11 | Диалог, где все неправы | `closest_to_truth` назван, но `conclusion` прямо говорит, что истина вне позиций собеседников |
| 12 | Диалог с анонимизацией, имя «Иван» упомянуто в реплике Марии («Иван прав») | В тексте, репликах аналитиков и вердикте — только «Собеседник А»; `legend = {"Собеседник А": "Иван", …}` только в ответе 202 |
| 13 | `ANONYMIZE_PARTICIPANTS=false` | Имена проходят как есть, `legend = {}` |
| 14 | Сообщение судье у разбора `running` или `failed` | 409 |
| 15 | Второе сообщение, пока судья отвечает на первое | 409 |
| 16 | Сообщение «Иван не прав» в диалоге с `legend = {"Собеседник А": "Иван"}` | Модель и БД получают «Собеседник А не прав» |
| 17 | Пользователь возражает без доводов («вы ошибаетесь, и всё») | Судья сохраняет оценку и объясняет почему; не извиняется и не уступает |
| 18 | Публикация разбора `running` или `failed` | 409 |
| 19 | Публикация диалога с `legend = {"Собеседник А": "Иван"}` | В снимке только «Собеседник А»; «Иван» не встречается нигде |
| 20 | В материале `<script>alert(1)</script>` | В снимке текст экранирован, `<script>` в странице нет |
| 21 | Удаление опубликованного разбора | Снимок удаляется из хранилища до удаления разбора; ссылка перестаёт открываться |

## 7. Declared heuristics and assumptions

Значения зеркалятся в `config.py`; менять здесь и там в одном коммите.

| Константа | Значение | Обоснование |
|---|---|---|
| `DEFAULT_ROUNDS` | 2 | 1 независимый + 1 перекрёстный: минимум, при котором видна реакция друг на друга |
| `MAX_ROUNDS` | 3 | 10 вызовов LLM на разбор — потолок по времени ожидания в UI |
| `MAX_TEXT_CHARS` | 20 000 | ~5k токенов текста × 3 аналитика × раунды: укладывается в контекст и бюджет |
| `MODEL_ANALYST` | `anthropic/claude-opus-5-5` | Ключ Anthropic — основной у пользователя; Opus 5.5 — текущая модель линейки |
| `MODEL_JUDGE` | `anthropic/claude-opus-5-5` | Судья должен быть не слабее аналитиков |
| `ANALYST_EFFORT` / `JUDGE_EFFORT` | `medium` / `high` | Opus 5.5: thinking всегда включён, effort — единственный регулятор; судье — больше |
| `TURN_MAX_TOKENS` | 6 000 (мин. 1 024) | На Opus 5.5 thinking входит в лимит; реплика ≤ ~1 500 токенов + запас. Ниже минимума приложение не стартует |
| `JUDGE_NARRATIVE_WORDS` | 400–800 | Развёрнутое обоснование: меньше — ярлыки без аргументов, больше — пересказ транскрипта |
| `JUDGE_MAX_TOKENS` | 16 000 (мин. 4 096) | Структурированный вердикт + thinking; при 900 JSON обрывался (живой прогон 2026-10-11) |
| `DEEPSEEK_TEMPERATURE` | 0.3 | Аналитика, не креатив; Anthropic temperature не принимает (SDK 1.13) |
| `LLM_CONCURRENCY` | 3 | Параллельный раунд 1 — ровно три вызова |
| `DEEPSEEK_MAX_RETRIES` | 2 | Зеркалит дефолт ретраев Anthropic SDK; httpx сам не ретраит (408/409/429/5xx, сетевые) |
| `DEEPSEEK_TIMEOUT_S` | 600 | Reasoner отвечает минутами |
| `RUNS_KEPT_IN_MEMORY` | 50 | Завершённые разборы в памяти для быстрого replay SSE; дальше — из БД |
| `SSE_HEARTBEAT_S` | 15 | Прокси обрывают тихие соединения на 30–60 с |
| `HISTORY_LIMIT` | 50 | Боковая панель истории |
| `TITLE_CHARS` | 80 | Заголовок в истории |
| `DIALOGUE_LINE_SHARE` | 0.6 | Доля строк с автором, при которой `auto` считает ввод диалогом: ниже — цитаты внутри обычного текста |
| `DIALOGUE_NAME_CHARS` | 40 | Длиннее — это не имя, а фраза с двоеточием |
| `DIALOGUE_MIN_MESSAGES` | 4 | Экспорт чата: имя на своей строке, тело в 5–20 строках — доля строк с автором мала, но 4 реплики от ≥ 2 людей — уже диалог (живой случай 2026-10-11) |
| `JUDGE_CHAT_EFFORT` | `medium` | Ответ на вопрос по готовому разбору — не новый вердикт; в чате важнее время ответа, глубина `high` — для самого вердикта |
| `JUDGE_CHAT_MAX_TOKENS` | 6 000 (мин. 1 024) | Как у реплики аналитика: ответ ≤ ~1 000 токенов + thinking |
| `JUDGE_CHAT_WORDS` | 80–300 | Ответ в чате, не второй вердикт; подробнее — по просьбе пользователя |
| `JUDGE_CHAT_MAX_CHARS` | 2 000 | Сообщение в чате — вопрос или довод, не новый материал (для него — новый разбор) |
| `JUDGE_CHAT_TIMEOUT_S` | 180 | Ответ судьи в чате — реплика размера аналитика (18–30 с на Opus 5.5); таймаут SDK — минуты, и всё это время висела бы блокировка разбора |
| `JUDGE_CHAT_MAX_MESSAGES` | 20 | Сообщений пользователя на разбор: каждое — полный контекст разбора в модель |
| `SHARE_BUCKET` | пусто | Бакет GCS для снимков (ADR-006); пусто — локальный каталог `SHARE_DIR` |
| `SHARE_DIR` | `./shared` | Каталог снимков без GCS; приложение раздаёт его по `/shared/` |
| `SHARE_TOKEN_BYTES` | 16 (16..48) | 128 бит случайности: ссылку нельзя угадать или перебрать; больше 48 байт ключ не помещается в колонку (64 символа) |
| `SHARE_CACHE_MAX_AGE_S` | 60 | Сколько снятая с публикации страница ещё может отдаваться из кэшей |
| `ANONYMIZE_PARTICIPANTS` | true | Имена собеседников — персональные данные; модель и БД видят только метки (§4.0b) |
| `LANGUAGE` | русский | язык реплик |

## 8. Observability

Логи через `logging` (структура `%(asctime)s %(levelname)s %(name)s: %(message)s`). На
каждый вызов LLM — строка `llm.call provider=<p> model=<m> role=<analyst|judge|chat>
analysis=<id> round=<n> ms=<t> in=<tokens> out=<tokens>`; на завершение разбора —
`analysis.done id=<id> status=<s> ms=<t> calls=<n>`. Токены — как отдал провайдер
(`usage`), без оценок. `/health` отдаёт версию из `pyproject`.

## 10. Acceptance criteria / Definition of Done

- `uv run pytest` зелёный: контракт API (§3), пайплайн на фейковом провайдере (§4),
  edge cases §6 №1–4, 6–7, 18–21 (публикация на фейковом хранилище).
- Ручная проверка в mock-режиме: текст → три реплики × 2 раунда → вердикт в UI; история;
  перезагрузка страницы восстанавливает разбор.
- Done, когда с живым ключом Anthropic разбор проходит до вердикта (ручной прогон,
  результат записан в README «Measurements»).
