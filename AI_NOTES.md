## What I accepted

- 2026-10-11, перезапуск проекта как Rational Check: пользователь описал продукт в
  одном сообщении (рациональные аналитики без философских школ, судья, простой UI,
  Anthropic основной + DeepSeek опцией). Агент предложил три методологические линзы
  вместо одинаковых агентов (ADR-002) и SSE вместо polling (ADR-003).

- 2026-10-11, загрузка `.txt` / `.md`: на вопрос «приложение обрезает текст?» агент нашёл,
  что сервер не режет, а `maxlength` поля молча отбрасывает вставку сверх 20 000 символов.
  Файлы сделаны чтением в браузере без нового API: сервер получает тот же `text`, а файл
  сверх лимита отклоняется с числом символов, а не режется. Фолбэк на Windows-1251 —
  потому что русские `.txt` из «Блокнота» часто не в UTF-8. Проверено в браузере
  синтетическими файлами (UTF-8/CRLF, 1251, UTF-16, ровно 20 000, 20 001, `.pdf`, NUL);
  JS-тестов в проекте нет. Бот файлы пока не принимает.

- 2026-10-11, лимит текста 20 000 → 200 000: пользователь попросил убрать лимит, «если
  слишком для модели — батчами». Агент замерил `count_tokens` на реальном диалоге
  (2,43 символа/токен) и сверился с контекстом Opus/Sonnet 5.5 (1M): 200k символов ≈ 82k
  токенов, батчи не нужны. Батчи отвергнуты: части теряют связи между репликами, а судье
  нужна вся картина. Потолок оставлен из-за цены: текст оплачивается в каждом вызове.
  Prompt caching записан в Cut scope. `maxlength` у поля убран — вместо молчаливой обрезки
  красный счётчик и ошибка при отправке.

- 2026-10-11, prompt caching (ADR-007): пользователь сказал «делай». Агент вынес линзу из
  `system` в начало задания и материал — в отдельный блок с `cache_control`, чтобы префикс
  совпадал у всех вызовов аналитиков, и добавил прогрев `max_tokens=0` перед параллельным
  раундом. Без прогрева три параллельных вызова записали бы кэш трижды. Проверено на живом
  API за несколько центов: прогрев пишет 8 871 токен, следующие вызовы читают их целиком;
  часовой TTL чата пишется и читается. Отвергнуто автоматическое кэширование: точка
  встала бы на уникальное задание, и чтений не было бы. Бот пользователь попросил не трогать.

- 2026-10-11, отказ модели: пользователь получил «Модель отказалась разбирать этот текст» на
  споре о негативных эмоциях. Агент нашёл разбор в логах Cloud Run, воспроизвёл отказ
  (категория `bio` на полном файле — ложное срабатывание) и включил серверный
  `fallbacks: "default"`; вживую тот же запрос ответил `claude-opus-5`. Попутно всплыло,
  что парсер диалога нашёл в книжном markdown 91 «собеседника» — пользователь решил убрать
  парсер (отдельная ветка).

- 2026-10-11, парсер диалога удалён (ADR-008): на книжном markdown он нашёл 91
  «собеседника». Пользователь спросил, нужен ли парсер только для анонимизации; агент
  ответил, что ещё для режима «Авто» и списка собеседников в вердикте, и предложил три
  варианта. Пользователь выбрал «модели определяют собеседников + поле „Скрыть имена“».
  `auto` теперь разрешает судья, а `participants` и итоговый режим пишутся из вердикта.
  Колонка `participants` осталась в БД без миграции. Бот теряет автоматическое скрытие
  имён — принято («пофиг на бот»).

## What I rejected or rewrote

**Баги, пойманные глазами в браузере, а не тестами (2026-10-11).** Селектор `[data-rounds]`
во фронтенде цеплял кнопки выбора раундов, и карточки реплик рендерились внутри кнопки;
mock-провайдер выбирал линзу по слову «ФАКТЫ», которое есть и в Манифесте, — все три
реплики были одинаковыми; мобильная вёрстка уезжала по горизонтали. Все три нашлись при
ручном прогоне в mock-режиме через встроенный браузер; mock-баг закреплён тестом
(`test_round_one_replies_differ_per_analyst_lens`). Урок: контрактные тесты API не ловят
DOM-ошибки — визуальная проверка обязательна перед гейтом.

**Ревью python-architect (2026-10-11).** Независимый агент прошёл весь диф ветки:
критичных проблем нет, 9 предупреждений, 13 предложений. Приняты все предупреждения
(таймзона SQLite, валидация модели по списку, завершение задач при остановке, утечка
HTTP-клиентов, ретраи DeepSeek, ошибки внутри SSE, дедупликация реплик, нарезка сообщений
бота, лог `provider/model`) и дешёвые предложения (Literal-типы, ProviderError, константы
в SPEC §7, docstrings). Отложено: учёт токенов при падении парсинга вердикта и DTO-дубль
лимита вопроса — не влияют на поведение. Коммит `refactor(*): review fixes`.

**Смена концепции: истина вместо победителя (2026-10-11).** Пользователь после первого
живого прогона уточнил цель: никакого соревнования — ни между аналитиками, ни между
собеседниками; судья ищет самое близкое к истине; нужен режим диалога. Из вердикта удалены
оценки аналитиков и «самый рациональный», добавлены консенсус/открытые вопросы и оценка
близости каждого собеседника к истине с обязательным «что у него верно». Зафиксировано
ревизией ADR-002 и SPEC §3.3/§4.0. Урок: продуктовую цель («истина, не победа») стоило
вытащить до первой версии промптов — соревновательная рамка пришла из первой версии
проекта (философы, лидерборд), а не из постановки.

**Обсуждение вердикта с судьёй (2026-10-11).** Запрос пользователя — одна фраза («чтобы с
судьёй можно было обсудить результаты»). Решения агента, зафиксированные в ADR-005 и SPEC
§4.6: синхронный POST вместо SSE, контекст целиком в одном `user`-сообщении (порт не
меняется), вердикт неизменен — пересмотр живёт только в переписке, правило против
угодливости («меняю оценку только под весом доводов»), анонимизация вопросов по легенде из
браузера. Отвергнуто: пересчитывать вердикт по итогам чата (вердикт зависел бы от
настойчивости), чат с аналитиками. Ревью python-architect: приняты атомарная запись пары
реплик, блокировка до чтения записи (иначе устаревший счётчик лимита), таймаут ответа
(оборванный клиентом запрос держал бы блокировку минутами), 409 на удаление во время
ответа, подсказка при отсутствии легенды, тест на уникальность маркера mock. Отложено:
отдельное исключение вместо `ValueError` для 422 (так же устроен запуск разбора) и
`max_length` в DTO. Качество ответов судьи в чате не измерено — живого прогона не было.

**Публикация разбора (2026-10-11).** Запрос пользователя — одна фраза («чтобы можно было
поделиться с кем угодно»). Агент нашёл в README, что прод на Cloud Run целиком закрыт IAP,
поэтому ссылка на сам сервис постороннему не откроется. Перед кодом агент остановился и
задал три вопроса: механизм (снимок в публичный GCS, HTML-файл или маршрут в приложении),
состав (исходник, реплики, чат) и имена собеседников. Пользователь выбрал GCS-снимок,
исходник с репликами без чата и только метки. Решения агента, зафиксированные в ADR-006 и
SPEC §4.7: статический снимок вместо живой страницы (вердикт неизменен), порт
`SnapshotPublisher` с GCS и локальным каталогом, роль `legacyObjectReader` вместо
`objectViewer` (у последней есть листинг, и чужие публикации можно было бы перечислить),
рендер на сервере с экранированием и без JS, снятие публикации до удаления разбора (502 и
разбор остаётся, если хранилище недоступно). Отвергнуто: маршрут `/s/<token>` в
приложении (пришлось бы снимать IAP или поднимать второй сервис), подписанные URL (живут
не больше 7 дней), клиентский рендер снимка.
Ревью python-architect нашло то, что тесты на фейках не ловили. Принято: блокировка на
разбор вокруг публикации, снятия и удаления. Без неё двойной `POST` давал 500 на
уникальности, а удаление во время загрузки оставляло в бакете страницу без записи.
`question` теперь анонимизируется так же, как текст: раньше «Кто прав, Иван или Мария?»
ушёл бы в публичный снимок как есть. Строка про метки в снимке пишется, только если имена
действительно метки. Ещё приняты: том для снимков в `docker compose`, создание `SHARE_DIR`
при старте (до первой публикации `/shared/…` отдавал 500), ошибки ключа и хранилища →
502 с фиксированным текстом без бакета и путей, `if_generation_match=0` (повторы
загрузки и запрет перезаписи), CSP в странице, границы `SHARE_TOKEN_BYTES`, тест
экранирования всех строковых полей вердикта. Отложено: `PRAGMA foreign_keys` для SQLite
(гонку закрывает блокировка, а включать FK на старой базе — отдельный риск) и сирота в
бакете при отмене запроса посреди загрузки (поток всё равно дозальёт объект; редкий случай
для личного инструмента). Живой прогон с настоящим бакетом не делался: бакета пока нет.

## Where I stopped the agent

- Живой прогон с ключом Anthropic тратит деньги — делается только по явному «да».
- Публикация: агент спросил про механизм, состав и имена до первой строки кода. Создание
  публичного бакета и IAM в GCP — только по явному «да» (это открывает данные наружу).

## Honest assessment of the division of labor

Продуктовая постановка — человек. Архитектура, промпты, фронтенд — агент по SPEC;
качество промптов не измерено до eval.
